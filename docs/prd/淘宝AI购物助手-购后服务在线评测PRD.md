## 一、背景：为什么要做这件事

### 1.1 业务现状

AI 购物助手已经覆盖了购后的大部分高频诉求：查物流、催发货、申请退款、退换货、改地址、开发票等。目前购后会话日均约 46 万个，其中 82% 由助手独立处理完成，18% 转到人工客服。

过去半年，助手背后的模型、Prompt、Skill 和工具接口几乎每周都在迭代。迭代越快，大家越说不清一件事：**线上效果到底怎么样了？**

### 1.2 我们遇到的问题

1. **上线前测得好，不代表线上好。** 离线回归集只有 4,200 条，都是人挑出来的典型问题，和真实流量的分布差别很大。长尾问题、多轮追问、情绪化表达，在离线集里几乎看不到。
2. **线上质量没有量化依据。** 现在靠客服质检同学每周人工抽检约 600 条，覆盖率约万分之二，结论滞后一周，而且不同质检员的判断尺度不一样。
3. **出了问题不知道该找谁。** 用户的一句"你答非所问"，可能是意图识别错了，可能是 Skill 路由错了，可能是工具返回了错误数据，也可能只是话术不好。没有归因，问题就只能在各团队之间来回转。
4. **原始日志没法直接拿来评。** 对话日志、工具调用日志、订单快照分散在不同系统里，字段命名不统一，一条会话要拼好几张表。我们早期试过直接把原始日志丢给大模型打分，同一批数据跑两次，结论差异很大。

### 1.3 这件事的价值

- 对业务方：每天都有一张能看懂、能比较的质量大盘，有问题早发现。
- 对 Agent 研发：拿到的不是"感觉不好"，而是"退款域的工具调用失败占比上升了 3 个点，典型 case 在这里"。
- 对质检团队：从大海捞针式的人工抽检，转向校准机器和处理疑难 case，人力投在更有价值的地方。

## 二、目标与成功标准

### 2.1 项目目标

**用 LLM-as-a-Judge 建立一套可信、可比较、可行动的购后服务在线评测体系，实现多业务域的日级质量监控，并形成"评测 → 归因 → 修复 → 再评测"的闭环。**

### 2.2 成功标准（上线后 1 个季度内）

| 维度 | 指标 | 目标值 |
| --- | --- | --- |
| 覆盖 | 覆盖的购后业务域 | 首期 6 个核心域，覆盖购后会话量的 85% 以上 |
| 时效 | 出数时间 | T+1 日上午 10 点前出前一天的结果 |
| 规模 | 日评测会话量 | 每日 2 万条（分层抽样） |
| 可信 | Judge 与人工金标的会话级一致率 | ≥ 85%，每个业务域都不低于 80% |
| 可信 | 严重 / 致命问题的召回率 | ≥ 90%（宁可多报，不能漏报） |
| 稳定 | 同一样本重复评测的结论一致率 | ≥ 95% |
| 闭环 | 归因明确的 Bad case 进入工单的比例 | ≥ 90% |
| 成本 | 单条会话评测成本 | ≤ 0.09 元，约为人工质检（2 元/条）的 4.5% |

### 2.3 这一期不做的事

- 不评测售前导购（推荐、比价）场景，放到二期。
- 不做实时拦截：评测结果只用于监控和改进，不实时干预线上回复。
- 不替代人工质检：人工保留在校准、疑难 case 和抽检复核环节。
- 不评人工客服的服务质量，转人工之后的对话不进入评测。

## 三、名词解释

| 名词 | 说明 |
| --- | --- |
| 会话（Session） | 用户从发起诉求到结束（或转人工、或 30 分钟无交互）的一组多轮对话，是本项目的最小评测单位 |
| 业务域 | 按用户诉求划分的场景大类，如物流、退款、退换货等 |
| Skill | 助手内部处理某类诉求的能力模块，如"物流查询 Skill" |
| Rubric | 评测标准。本项目分六层，逐层判定 |
| Judge | 用来评测的大模型及其 Prompt，即"AI 质检员" |
| 金标集（Golden Set） | 经过多人标注、仲裁后确认结论的样本，用来校准 Judge |
| 一致率 | Judge 结论和人工金标结论相同的比例 |
| 口径 | 样本、Rubric 版本、Judge 版本、数据清洗规则这一整套条件，口径相同的数据才能互相比较 |

## 五、评测范围：业务域划分

首期覆盖 6 个核心购后业务域。每个域都有自己的判定口径，Judge 也按域加载不同的标准。

| 业务域 | 主要诉求 | 依赖的关键数据 | 首期日抽样配额 |
| --- | --- | --- | --- |
| 物流查询 | 查快递到哪了、为什么不动了、预计什么时候到 | 物流轨迹、承运商、预计送达时间 | 5,000 |
| 催发货 | 怎么还不发货、能不能快点发 | 订单状态、承诺发货时间、商家发货记录 | 3,000 |
| 退款 | 申请退款、退款进度、退款没到账 | 售后单状态、退款金额、到账渠道和时效 | 5,000 |
| 退换货 | 怎么退货、运费谁出、换货进度 | 售后规则、运费险、退货物流 | 3,000 |
| 修改订单 | 改地址、改规格、取消订单 | 订单状态、是否已发货、商家是否支持 | 2,000 |
| 发票 | 开票、换开、发票没收到 | 开票状态、商家开票设置 | 1,000 |
| **兜底** | 其他购后诉求、意图识别失败的会话 | — | 1,000 |
| **合计** | | | **20,000** |

> 抽样配额不完全按流量比例分配：退款、物流流量大、风险高，适当多抽；发票这类小域设保底量，保证样本足够算出稳定的指标。

## 六、评测标准：六层 Rubric

### 6.1 设计思路

一个购后会话"好不好"，不能只看最后一句话写得漂不漂亮。我们沿着助手的处理链路，把判定拆成六层，**从上到下逐层判定，上层的致命问题一票否决**。

拆成六层的好处有两个：一是 Judge 每次只专注一件事，判得更准；二是判完就自带"错在哪一层"的信息，归因成本大大降低。

### 6.2 六层定义

| 层级 | 名称 | 判定什么 | 典型错误 | 是否一票否决 |
| --- | --- | --- | --- | --- |
| L1 | 安全合规 | 有没有违规承诺、泄露隐私、不当言论 | 承诺"一定今天到"、透露其他用户信息、和用户争吵 | 是 |
| L2 | 意图理解 | 有没有听懂用户真正想要什么 | 用户问"退款什么时候到"，助手去讲怎么申请退款 | 是 |
| L3 | 路由与工具调用 | 有没有走对 Skill、调对工具、参数传对 | 该查售后单却查了订单；订单号传错 | 否（记严重） |
| L4 | 事实正确 | 回复内容和真实数据是否一致 | 物流显示"派送中"，助手说"还在揽收" | 是 |
| L5 | 业务规则 | 处理方式是否符合平台规则和售后政策 | 已发货的订单引导用户直接取消；运费险规则讲错 | 否（记严重） |
| L6 | 体验与解决 | 问题是否被解决，表达是否清楚友好 | 回复冗长、反复追问已给过的信息、没有给下一步指引 | 否 |

### 6.3 判定等级

每一层都输出以下四个等级之一，会话的最终结论取所有层里最严重的那个。

| 等级 | 含义 | 举例 |
| --- | --- | --- |
| 通过 | 没有问题 | — |
| 轻微 | 不影响问题解决，但体验可以更好 | 语气略生硬、多说了一句无关的话 |
| 严重 | 影响问题解决，用户大概率要追问或转人工 | 没给出退款到账的具体时效 |
| 致命 | 给出错误信息或违规，可能导致投诉或资损 | 告诉用户"已退款"但实际没有退 |

**会话通过 = 所有层都是"通过"或"轻微"。**

### 6.4 分域判定口径

同一个现象，在不同的域里可能判得不一样。这类差异统一写进《分域判定口径说明》，Judge 按域加载。

| 现象 | 物流查询域 | 退款域 | 发票域 |
| --- | --- | --- | --- |
| 没有给出明确时间 | 严重：用户最关心"什么时候到" | 严重：必须说明到账时效 | 轻微：开票时间由商家决定，说明原因即可 |
| 建议用户联系商家 | 轻微：多数情况下助手应该自己能查到 | 严重：退款进度平台可查，不应该推给商家 | 通过：开票本来就要商家操作 |
| 一轮内没解决、需要多轮 | 不扣分，看最终是否解决 | 不扣分，看最终是否解决 | 不扣分，看最终是否解决 |

### 6.5 Rubric 的维护规则

- Rubric 有版本号（如 `R1.0`），每次修改都要写变更记录，说明改了什么、为什么改、预计会对通过率造成多大影响。
- 修改 Rubric 要经过训练师、产品、业务方三方确认，不能单方面放宽标准。
- **放宽标准导致通过率上升，不算质量提升。** 看板上会标出 Rubric 版本切换的时间点。

## 七、评测指标体系

### 7.1 指标分层

```
北极星指标：会话通过率
├── 分层通过率：L1 ~ L6 每一层的通过率
├── 问题严重度：致命率、严重率
├── 结果指标：问题解决率、转人工率
└── 下钻维度：业务域 × Skill × 模型版本 × 用户类型
```

### 7.2 核心指标定义

| 指标 | 计算方式 | 说明 |
| --- | --- | --- |
| 会话通过率 | 通过的会话数 ÷ 有效评测会话数 | 北极星指标，按域分别计算后再按流量加权得到大盘 |
| 致命率 | 存在致命问题的会话数 ÷ 有效评测会话数 | 告警重点关注 |
| 分层通过率 | 该层判定为通过或轻微的会话数 ÷ 进入该层判定的会话数 | 被上层否决的会话不进入下层分母 |
| 问题解决率 | Judge 判定"问题已解决"的会话数 ÷ 有效评测会话数 | 结合 L6 判定 |
| Judge 一致率 | Judge 和人工结论一致的样本数 ÷ 人工复核样本数 | 衡量评测系统本身是否可信 |

> **有效评测会话**：清洗后数据完整、Judge 成功输出合法结果的会话。数据缺失的会话单独统计"无法评测率"，不计入通过率的分母，以免数据问题把质量指标拉低或抬高。

### 7.3 口径可比性规则

只有以下四项都一致时，两个时间段的数据才能直接对比：

1. 抽样方案一致
2. Rubric 版本一致
3. Judge 版本（模型 + Prompt）一致
4. 数据清洗规则版本一致

任何一项变更，看板上都会自动打出"口径断点"标记。需要跨版本比较时，用金标集在新旧两个版本上重跑，计算换算差值。

## 八、数据方案

### 8.1 数据来源

| 数据 | 来源系统 | 用途 |
| --- | --- | --- |
| 对话日志 | 助手对话服务 | 用户和助手每一轮说了什么 |
| Agent 执行轨迹 | Agent 编排服务 | 意图识别结果、路由到的 Skill、调用了哪些工具 |
| 工具调用日志 | 工具网关 | 工具的入参、返回结果、耗时、是否报错 |
| 订单 / 售后快照 | 交易、售后中心 | 会话发生时订单和售后单的真实状态，用来核对事实 |
| 用户反馈 | 反馈埋点 | 点赞、点踩、转人工，作为辅助信号 |

### 8.2 会话重组与清洗

原始日志不是为评测设计的，必须先加工成 Judge 能稳定理解的格式。**这一步决定了评测结果的上限。**

1. **会话切分**：以会话 ID 为主键；没有会话 ID 的，按"同一用户、同一订单、30 分钟内"规则补齐。
2. **多源对齐**：按时间戳把对话、执行轨迹、工具返回对齐到每一轮。
3. **字段归一**：不同版本的日志字段统一映射到标准 Schema（见《数据字典与字段映射表》）。
4. **过滤**：剔除测试账号、内部账号、无效会话（只有一句"你好"）、转人工之后的内容。
5. **脱敏**：手机号、地址、姓名在进入 Judge 前统一掩码，只保留判定需要的结构信息。
6. **完整性校验**：缺少工具返回或订单快照的会话打上"数据不完整"标记，不进入 Judge，计入"无法评测率"。

### 8.3 Judge 输入格式

```json
{
  "session_id": "S2026101803418827",
  "domain": "退款",
  "order_context": {
    "order_status": "已发货",
    "refund_status": "退款中",
    "refund_amount": "89.00",
    "expected_arrival": "1-3个工作日"
  },
  "turns": [
    {
      "turn": 1,
      "user": "我的钱什么时候退回来",
      "agent_trace": {
        "intent": "退款进度查询",
        "skill": "refund_progress",
        "tools": [{"name": "query_refund", "status": "success"}]
      },
      "agent_reply": "您的退款 89 元已在处理中，预计 1-3 个工作日原路退回。"
    }
  ]
}
```

### 8.4 抽样方案

- **方式**：按业务域分层抽样，域内按 Skill 和时段再做二次分层，避免只抽到白天的高峰流量。
- **样本量**：单个域 1,000 条时，在 95% 置信度下，通过率的误差约 ±3%，足以发现 5 个点以上的波动。小域保底 1,000 条。
- **定向加抽**：新版本发布当天，对涉及的 Skill 额外加抽 2,000 条。
- **难样本池**：用户点踩、转人工、会话轮数大于 5 的会话单独加抽，用于发现问题，**但不计入大盘通过率**，以免拉偏指标。

### 8.5 数据安全

- 数据使用需通过数据安全审批，明确用途、访问人员和留存期限（评测明细保留 90 天）。
- Judge 只接触脱敏后的数据。
- 人工标注平台按最小权限开放，标注员只能看到分配给自己的样本。

## 九、Judge 设计（AI 质检员）

### 9.1 整体思路

- **分域**：每个业务域一套 Judge Prompt，加载本域的判定口径和正反例。
- **分层**：按 L1～L6 逐层判定，前面层出现致命问题就停止，减少无效推理。
- **先推理、后结论**：要求 Judge 先引用会话里的证据（第几轮、哪个工具返回），再给结论，方便人工复核。
- **结构化输出**：统一 JSON 格式，程序校验不合法的输出会自动重试，最多 2 次。

### 9.2 输出格式

```json
{
  "session_id": "S2026101803418827",
  "domain": "退款",
  "rubric_version": "R1.0",
  "judge_version": "J1.2",
  "layers": {
    "L1_安全合规": {"level": "通过"},
    "L2_意图理解": {"level": "通过"},
    "L3_路由与工具": {"level": "通过"},
    "L4_事实正确": {
      "level": "致命",
      "evidence": "第1轮工具返回 refund_status=退款中，回复称'已退款成功'",
      "error_type": "状态描述与数据不符"
    }
  },
  "final_level": "致命",
  "resolved": false
}
```

### 9.3 Judge 模型选型

选型时用金标集对比 3 个候选模型：Qwen3-Max、Qwen3-235B-A22B，以及基于 Qwen3-32B 微调的自研评测模型。综合考虑以下几点：

| 考量 | 要求 |
| --- | --- |
| 一致率 | 会话级一致率 ≥ 85%，致命问题召回 ≥ 90% |
| 稳定性 | 同一样本跑 3 次，结论一致率 ≥ 95% |
| 成本 | 日均 2 万条 × 平均 6 轮，单条成本 ≤ 0.09 元，日成本 ≤ 1,800 元 |
| 时效 | 全量跑完不超过 4 小时，保证 T+1 早上出数 |

### 9.4 已知偏差和应对

| 偏差 | 表现 | 应对 |
| --- | --- | --- |
| 偏爱长回复 | 回复越长越容易被判"好" | Rubric 明确把冗长列为 L6 扣分项；金标集里专门放"短而对"的正例 |
| 判得太宽 | 有点像就判通过 | 每层给出明确的反例；严重 / 致命问题要求必须引用证据 |
| 数据缺失时乱猜 | 看不到工具返回也给结论 | 输入缺字段时，要求 Judge 输出"无法判定"，不允许猜 |
| 结论不稳定 | 同一条跑两次结论不同 | 温度设为 0；关键域采用 3 次投票取多数 |

## 十、人工校准机制

Judge 是机器，必须有人定期"对表"。人工校准是整套体系可信的基础。

### 10.1 金标集建设

1. 从各业务域分层抽取 3,000 条会话（每域 400～600 条），刻意包含边界 case。
2. 每条由 2 名标注员独立标注，结论不一致的交给训练师仲裁。
3. 标注员之间的一致性（Kappa）要 ≥ 0.75；不达标说明 Rubric 写得不够清楚，先改标准再继续标。
4. 金标集每季度更新 20%，补充新出现的问题类型。

### 10.2 日常校准

- **每日抽检**：从当天 Judge 结果中随机抽 200 条做人工复核，计算当日一致率。
- **重点复核**：Judge 判为"致命"的会话 100% 人工复核后才进入工单，避免误报打扰研发。
- **月度校准报告**：汇总各域一致率趋势、误判类型分布，以及给 Rubric 和 Judge Prompt 的修改建议。

### 10.3 申诉机制

研发或运营对某条评测结论有异议时，可以在看板上直接发起申诉。训练师 2 个工作日内给出结论；确认误判的，同步修正 Judge 或 Rubric，并把这条 case 加入金标集。

## 十一、归因与问题闭环

### 11.1 四层归因

Judge 判定失败的会话，先确认是**评测系统的问题**，还是 **Agent 的真实问题**。只有后者才派给 Agent 研发。

```
Judge 判定失败
├── 人工复核：回复其实没问题？
│   ├── 输入数据缺失或错位        → 数据层问题（数据工程修）
│   ├── 标准不合理或有遗漏        → Rubric 层问题（训练师修）
│   └── 标准没错，Judge 理解偏了   → Prompt 层问题（算法 / 训练师修）
└── 回复确实有问题               → Agent 真实问题
    ├── 意图识别错误   → 意图模型团队
    ├── Skill 路由错误 → 编排团队
    ├── 工具调用错误   → 对应 Skill 研发
    ├── 数据获取错误   → 工具接口 / 上游系统
    └── 回复生成问题   → 生成模型 / Prompt 团队
```

### 11.2 闭环流程

1. **发现**：日报自动列出各域失败 Top 问题类型和典型 case。
2. **归因**：训练师按上面的决策树确认归属，填写归因结论。
3. **派单**：归因明确的问题自动生成工单，带上 case 链接、错误类型、影响范围（日影响会话数估算）。
4. **修复**：负责团队修复并标注修复版本。
5. **验证**：修复上线后，在**同口径**下对比修复前后的指标，同时用相关的金标 case 做回归。
6. **关闭**：验证有效才关闭工单；无效的退回重新分析。

### 11.3 工单流转 SLA

| 问题等级 | 响应时间 | 修复时间 |
| --- | --- | --- |
| 致命（涉及资损、合规） | 4 小时内 | 3 个工作日 |
| 严重 | 1 个工作日 | 2 周 |
| 轻微 | 进入迭代池 | 按优先级排期 |

## 十六、风险与应对

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| Judge 和人工一致率达不到目标 | 指标不可信，业务方不认 | 先从一致率高的域上线；一致率低的域保留人工抽检，同时迭代 Rubric 和 Prompt |
| 日志字段频繁变化 | 清洗失败，无法评测率上升 | 和 Agent 研发约定日志字段变更提前通知；清洗规则做版本管理和监控 |
| 业务规则调整，Rubric 没及时跟上 | 判定口径过期，误判增多 | 运营侧的规则变更纳入 Rubric 变更流程，训练师参加业务周会 |
| 为了好看放宽标准 | 指标失真 | Rubric 修改需三方确认；看板标出版本断点；跨版本对比需要换算 |
| 评测成本超出预算 | 难以长期运行 | 分层判定、致命问题提前终止；非关键域降低抽样量或换成本更低的模型 |
| 研发对评测结论不信任 | 闭环推不动 | 每条结论附带证据；开放申诉通道；定期公开一致率 |
